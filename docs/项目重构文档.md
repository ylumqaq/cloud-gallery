# 云图库项目技术文档

## 一、项目概述

- 定位：类似「云盘 / 团队图库」的企业级图片管理系统，支持图片上传与管理、私有空间与团队空间，团队空间带细粒度成员权限控制，为支撑海量图片设计了分库分表方案。
- 技术形态：单体 Spring Boot 后端项目（前端不在本仓库）
- 端口：`8123`，上下文路径 `/api`

## 二、技术栈

| 分类    | 技术                           | 用途               |
| ----- | ---------------------------- | ---------------- |
| 基础框架  | Spring Boot 3.5.16 + Java 17 | 后端主体             |
| ORM   | MyBatis-Plus 3.5.17          | 增删改查、分页、逻辑删除     |
| 缓存    | Redis + Spring Session       | 分布式会话登录态 + 多级缓存  |
| 本地缓存  | Caffeine                     | 多级缓存（本地 + Redis） |
| 权限认证  | Sa-Token 1.45.0              | 登录态 + 细粒度权限鉴权    |
| 数据库   | MySQL 8.0.42                 | 业务数据存储           |
| 向量检索  | PostgreSQL 18.3 + pgvector   | 图片向量存储与相似度检索     |
| 分库分表  | ShardingSphere 5.5.3         | 图片表按空间水平分表       |
| 对象存储  | 腾讯云 COS                      | 图片文件存储           |
| 图片处理  | 腾讯云数据万象 CI                   | 图片处理 + 图片向量特征提取  |
| 工具/其他 | Jsoup、Hutool、Knife4j、Lombok  | 网页解析、工具、接口文档     |

## 三、系统分层架构

```
controller（接口层，@RestController + 权限注解）
    ↓
service（业务层，接口 + impl 实现）
    ↓
manager（第三方/通用能力封装：COS、上传、鉴权、分表）
    ↓
mapper（数据访问层，MyBatis-Plus BaseMapper）
    ↓
MySQL / Redis / 腾讯云 COS
```

设计原则：

- **controller 只做参数接收与结果返回**，不写业务。
- **service 写业务逻辑**，事务、校验、组装都在这一层（事务边界与一致性策略见《事务设计文档》）。
- **manager 封装可复用能力**（如 CosManager、上传模板、权限管理器），与业务解耦。
- **统一返回** **`BaseResponse`** **+ 统一异常** **`GlobalExceptionHandler`**。
- **模块边界清晰**：按业务域（用户/图片/空间/权限）划分模块，模块间只通过接口交互，避免跨模块直接操作对方的表或实现，为将来拆分微服务留好边界。

### 模块化与可拆分性

采用**模块化单体**策略：先以单个 Spring Boot 应用部署，但代码按业务域划分清晰模块，为将来演进为微服务保留拆分能力。

- **业务域分模块**：用户、图片、空间、权限、分析等模块在包结构上保持独立。
- **接口隔离**：模块间只通过 service 接口交互，不跨模块调用对方的 impl 或 mapper。
- **数据归属清晰**：谁的表谁负责，图片模块不直接操作空间的表，权限模块不直接 join 图片表。
- **演进路径**：单体 → 模块化单体 → 按模块逐个抽离为微服务（优先拆分最独立的模块，如空间分析）。

## 五、模块详细设计

### 模块一：认证与权限控制（Sa-Token + RBAC）

#### 1. 业务背景

本项目用 Sa-Token 承载两套相互独立的认证体系：

- **用户登录认证**（默认 `StpUtil`）：负责「用户是否登录」，登录态存 Redis（Spring Session），面向所有接口做登录校验。
- **空间权限控制**（`StpKit.SPACE`）：负责「用户在空间里能做什么」，基于团队空间角色（RBAC），面向空间内图片、成员操作做细粒度鉴权。

两套体系通过独立的 `StpLogic` 隔离，互不干扰。

项目里有三种图库场景：

- **公共图库**（`spaceId` 为空）：所有人可看，但只有图片作者和管理员能改。
- **私有空间**：只有空间创建者和管理员能操作。
- **团队空间**：空间内有 `viewer / editor / admin` 三种角色，不同角色能做的操作不同。

为避免权限逻辑散落在各接口中，引入 **RBAC 权限模型 + Sa-Token 注解式鉴权**。

#### 2. 核心设计

**① 权限配置驱动（数据驱动，而非硬编码）**

权限和角色的对应关系放在 JSON 配置文件 `resources/biz/spaceUserAuthConfig.json` 里，运行时加载：

```json
{
  "permissions": [
    {"key": "spaceUser:manage", "name": "成员管理"},
    {"key": "picture:view",   "name": "查看图片"},
    {"key": "picture:upload", "name": "上传图片"},
    {"key": "picture:edit",   "name": "修改图片"},
    {"key": "picture:delete", "name": "删除图片"}
  ],
  "roles": [
    {"key": "viewer", "permissions": ["picture:view"]},
    {"key": "editor", "permissions": ["picture:view","picture:upload","picture:edit","picture:delete"]},
    {"key": "admin",  "permissions": ["spaceUser:manage","picture:view","picture:upload","picture:edit","picture:delete"]}
  ]
}
```

好处：新增角色或调整权限，**只改配置不改代码**。

**② 自定义权限注解**

封装 `@SaSpaceCheckPermission` 注解，本质是 `@SaCheckPermission` 的别名扩展，并指定独立的登录类型 `space`：

- `SaSpaceCheckPermission.java`
- `StpKit.java` 里定义 `SPACE = new StpLogic("space")`，将「空间权限体系」与「普通登录体系」分离。

**③ 动态权限加载**

实现 Sa-Token 的 `StpInterface`（`StpInterfaceImpl.java`），在鉴权时动态计算当前用户拥有的权限码：

1. 从当前请求解析出 `SpaceUserAuthContext`（包含 `pictureId / spaceId / spaceUserId`）。
2. 根据 `id` 对应的请求路径前缀（`picture` / `space` / `spaceUser`）判断该 id 的类型。
3. 按空间类型分支：
   - 公共图库 → 本人或管理员给全部权限，否则只有 `picture:view`。
   - 私有空间 → 本人或管理员给全部权限，否则无权限。
   - 团队空间 → 查 `space_user` 表拿到当前用户角色，再映射为权限列表。

接口上只需一行注解即可完成鉴权：

```java
@SaSpaceCheckPermission(value = SpaceUserPermissionConstant.PICTURE_UPLOAD)
public BaseResponse<PictureVO> uploadPicture(...) { ... }
```

#### 3. 核心流程（一次上传请求的鉴权链路）

```
请求 → Sa-Token 拦截器 → 命中 @SaSpaceCheckPermission
     → 调用 StpInterfaceImpl.getPermissionList(loginId, "space")
     → 从请求解析上下文(spaceId/pictureId)
     → 查库确定角色 → 角色映射权限码
     → 判断是否包含 "picture:upload" → 通过/拒绝
```

#### 4. 关键设计要点

- **一个** **`id`** **有歧义**：不同接口的 `id` 可能是图片 id、空间 id、成员 id，通过解析请求 URI 的模块前缀区分，塞进 `SpaceUserAuthContext` 对应字段。
- **三种场景权限规则不同**：在 `getPermissionList` 里用 `spaceType` 分支，收敛到一处。
- **登录体系隔离**：用 `StpKit.SPACE` 独立的 `StpLogic("space")`，避免与默认 `StpUtil` 登录态互相覆盖。
- 权限「配置化 + 注解化 + 动态加载」三位一体。

### 模块二：图片上传（模板方法 + 腾讯云 COS）

#### 1. 业务背景

图片既支持**本地文件上传**（`MultipartFile`），也支持**通过 URL 上传**（抓取网络图片）。两种方式流程高度相似，仅「获取文件」步骤不同。

#### 2. 核心设计：模板方法模式

用抽象类 `PictureUploadTemplate` 定义统一上传骨架，子类只实现差异化步骤：

```
uploadPicture(inputSource, pathPrefix)  // 模板方法，固定流程
  ├─ validPicture()          // 抽象：校验（子类实现）
  ├─ 生成安全上传路径          // 日期 + UUID + 后缀
  ├─ processFile()           // 抽象：获取/处理文件来源（子类实现）
  ├─ CosManager.putPictureObject()  // 上传到 COS 并触发 CI 图片处理
  ├─ 提取图片信息(宽高/格式/颜色)
  ├─ 封装 UploadPictureResult
  └─ 清理临时文件
```

两个子类：

- `FilePictureUpload`：校验文件大小 ≤ 2MB、格式（jpeg/png/jpg/webp），转存本地临时文件。
- `UrlPictureUpload`：校验 URL 协议、HEAD 请求确认存在、Content-Type、大小，再下载到本地。

业务层 `PictureServiceImpl.uploadPicture` 根据 `inputSource` 类型选择对应子类：

```java
PictureUploadTemplate tpl = filePictureUpload;
if (inputSource instanceof String) {
    tpl = urlPictureUpload;
}
```

#### 3. 图片处理与以图搜图

图片文件存储在 COS，基础图片处理（宽高/格式/主色调、webp 压缩、缩略图）由**数据万象（CI）** 提供。`CosManager.putPictureObject` 上传到 COS 后，一次同时完成：

- 获取原图宽高、格式、平均主色调（`IsPicInfo`）；
- 压缩为 webp 减小体积；
- 图片 > 2KB 时生成缩略图。

**以图搜图（MySQL + PostgreSQL 双库）**

图片元数据存 MySQL `picture` 表，特征向量存 PostgreSQL（pgvector），两者通过 `picture_id` 关联：

- **向量提取**：调用腾讯云数据万象 CI 的「图片向量特征提取」获取特征向量；
- **向量存储**：写入 PostgreSQL 的 `picture_embedding` 表（`picture_id` + `space_id` + `embedding`）；
- **相似检索**：在 PostgreSQL 用 pgvector 检索相似 `picture_id`，再回 MySQL 查完整图片信息。

```sql
-- PostgreSQL：启用扩展 + 建向量表 + HNSW 索引
CREATE EXTENSION IF NOT EXISTS vector;
CREATE TABLE picture_embedding (
    picture_id  BIGINT PRIMARY KEY,   -- 对应 MySQL picture.id
    space_id    BIGINT,               -- 冗余，用于「空间内」过滤
    embedding   vector(512)           -- 维度需与 embedding 模型一致
);
CREATE INDEX ON picture_embedding USING hnsw (embedding vector_cosine_ops);

-- 以图搜图：先在 PG 查相似 picture_id
SELECT picture_id FROM picture_embedding
WHERE space_id = :spaceId
ORDER BY embedding <=> :queryVector
LIMIT 20;
-- 再回 MySQL：SELECT * FROM picture WHERE id IN (...)
```

删除图片时需同步清理 PostgreSQL 向量（应用层双删 + 定时对账，无跨库事务，详见《事务设计文档》）。

#### 4. 关键设计要点

- 模板方法模式统一流程，新增上传来源只需新增子类，符合开闭原则。
- 职责分离：`CosManager`（对象存储）/ `PictureUploadTemplate`（流程）/ `PictureServiceImpl`（业务）三层清晰。

### 模块三：分库分表（ShardingSphere 自定义分片）

#### 1. 业务背景

随着图片量增长，单张 `picture` 表会越来越大，查询变慢。团队空间图片量大，因此按团队空间把图片拆分到不同物理表（`picture_空间id`）。

#### 2. 核心设计

**① 自定义分片算法**

`PictureShardingAlgorithm` 实现 ShardingSphere 的 `StandardShardingAlgorithm<Long>`，分片键为 `spaceId`：

- 精确分片 `doSharding`：`spaceId` 为 null → 落到逻辑表 `picture`（公共图库）；否则落到 `picture_{spaceId}`。
- 范围分片不需要实现（业务无范围查询场景，返回空集合）。

**② 动态分表管理器**

`DynamicShardingManager` 负责：

- 扫描所有团队空间，动态生成 `actual-data-nodes`（如 `cloud_gallery.picture_1,cloud_gallery.picture_2,...`）。
- 团队空间创建时，用 `CREATE TABLE picture_{spaceId} LIKE picture` 动态建表。
- 通过 ShardingSphere 的 `ContextManager` 在运行时 `alterRuleConfiguration` 更新分片规则。

#### 3. 关键设计要点

- 分表是动态的：团队空间不断新增，分表不能写死，需要「动态建表 + 动态刷新分片规则」。
- 自定义 `StandardShardingAlgorithm` 将「公共图库」与「各团队空间」的图片路由到不同表，隔离大数据量团队。

## 六、其他功能点

- **按颜色搜索**：上传时用数据万象 CI 提取图片主色调存库，查询时用 RGB 欧氏距离计算相似度排序（`ColorSimilarUtils`）。
- **空间统计分析**：用 MyBatis-Plus 的 `groupBy` + 聚合函数（`count(*)`、`sum(picSize)`、`DATE_FORMAT` 等）做分类、标签、大小、时间维度分析，以及空间用量排行 TopN。
- **批量抓取上传**：用 Jsoup 爬取必应图片搜索结果，解析后逐个走上传流程（`uploadPictureByBatch`）。
- **多级缓存**：Caffeine（本地缓存）+ Redis 两级缓存（有 `/cache/test` 测试接口演示）。
