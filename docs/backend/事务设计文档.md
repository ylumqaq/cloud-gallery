# 云图库事务设计文档

## 一、概述

本文档明确云图库各业务场景的事务边界、隔离级别与一致性策略，作为各模块实现事务逻辑的统一依据。

云图库的数据写入涉及三类存储，事务设计的核心难点在于**无法用单一数据库事务覆盖所有写入**：

| 存储 | 事务能力 | 一致性难点 |
| --- | --- | --- |
| MySQL（业务库） | 支持本地事务 | 多表写需显式声明事务边界 |
| 腾讯云 COS（对象存储 + CI 图库） | 无事务，非关系型外部服务 | 上传/删除不可回滚 |
| ShardingSphere（分表） | 单库分表可复用本地事务 | 动态建表与刷规则需保证顺序与原子性 |

## 二、事务总体策略

按「能否在同一数据库事务内保证一致性」划分两条策略线：

1. **强一致（本地事务）**：所有落在**同一个 MySQL 实例**内的多表写入，用 Spring 声明式事务（`@Transactional`）保证原子性。
2. **最终一致（外部存储）**：涉及 COS、CI 图库的写入，无法用本地事务覆盖，采用「本地事务 + 失败补偿 + 定时对账」保证最终一致。

总原则：

- **以 MySQL 为主数据源**：图片元数据、空间、用户等业务数据以 MySQL 为准，COS 文件与 CI 图库对象均为可重建/可补偿的副本。
- **先落主库，再落外部存储**：降低主库数据已提交但副本缺失的概率。
- **副本缺失可容忍、可修复**：CI 图库对象缺失仅影响搜图召回，COS 对象多余仅占存储，均可通过对账/补偿收敛。

## 三、单库本地事务（MySQL）

### 1. 使用方式

- 在 `service` 实现类的方法（或类）上加 `@Transactional`，遵循「service 层写事务」的分层约定。
- 默认传播行为 `REQUIRED`、隔离级别采用 MySQL 默认 `REPEATABLE READ`，无特殊需求不另行指定。

### 2. 事务边界场景

| 模块 | 方法 | 参与写入 | 说明 |
| --- | --- | --- | --- |
| 用户 | 注册 | 校验账号唯一 + `insert user` | 唯一索引 `uk_user_account` 兜底并发重复 |
| 空间 | 创建空间 | `insert space` + `insert space_user`（创建者 admin） | 两步必须原子，否则会出现「有空间无成员」 |
| 空间 | 删除空间 | 逻辑删除 `space` + 级联 `space_user` + 关联 `picture` | 多表逻辑删除需同事务 |
| 空间成员 | 添加/改角色/移除 | `insert/update/delete space_user` | 单表操作，事务可选，但建议显式声明 |
| 图片 | 编辑图片 | `update picture` | 单表更新 |
| 图片 | 删除图片 | 逻辑删除 `picture` | 见第四章，COS/CI 图库清理放事务外 |

> 注意：创建空间还伴随「动态建表 + 刷分片规则」，其原子性处理见第六章。

### 3. 隔离级别与并发

- 采用 MySQL 默认 `REPEATABLE READ`，配合逻辑删除与乐观/悲观锁场景：
  - **账号唯一性**：注册依赖 `uk_user_account` 唯一索引，插入冲突转友好错误，不依赖事务锁。
  - **空间成员唯一性**：依赖 `uk_space_user (space_id, user_id)` 唯一索引兜底重复添加。
  - 涉及「读-改-写」且存在竞态的业务（如空间用量扣减），后续按需引入版本号乐观锁或 `SELECT ... FOR UPDATE`，暂不在此文档展开。

## 四、外部一致性（MySQL + CI 图库）

### 1. 图片上传入图库

上传链路为「COS 上传 → MySQL 写 `picture` → CI 图库 addGalleryImage」，其中 CI 图库由腾讯云数据万象托管，与 MySQL 非同一系统，**无法共享事务**。写入顺序与补偿策略：

1. 在 **MySQL 本地事务**内插入 `picture` 元数据（提交后即视为「图片已存在」）。
2. 事务提交后，调用 `CosManager.addGalleryImage(原图对象键, 图片ID)` 把图片对象加入 CI 图库（entityId 保存图片 ID）。
3. 若步骤 2 失败：
   - **记录补偿日志**，由定时任务重试入图库；
   - 该图片在入图库前**不参与搜图**，但不影响图片浏览/管理。

### 2. 图片删除出图库

1. 在 **MySQL 本地事务**内逻辑删除 `picture`。
2. 事务提交后，从图片 URL 解析对象键，调用 `CosManager.deleteGalleryImage(对象键, 图片ID)` 出库。
3. 若步骤 2 失败，残留图库对象会成为「孤儿对象」，需依赖**定时对账**清理。

### 3. 定时对账任务

为收敛不一致，需实现一个对账任务（阶段 5 落地）：

- **方向一（补入图库）**：扫描 MySQL 中「未删除但 CI 图库中无对象」的 `picture_id`，补入图库。
- **方向二（删孤儿对象）**：扫描 CI 图库中「`picture_id` 在 MySQL 已删除或不存在」的对象，删除之。
- 对账幂等，可重复执行，避免重复写入/删除产生新脏数据。

### 4. 最终一致窗口说明

- 从「MySQL 提交成功」到「CI 图库入图库成功」之间存在短暂窗口，期间该图片**搜不到**（召回缺失），属可接受的最终一致。
- 删除同理：MySQL 已删但 CI 图库未删的窗口内，搜图可能命中已删除图片，回查 MySQL 详情时按「不存在」过滤即可（以 MySQL 为准）。

## 五、外部存储（COS）一致性

COS 无事务能力，采用「补偿清理」策略。

### 1. 上传

- 顺序：**先上传 COS → 再写 MySQL → 再加入 CI 图库**。
- 若 MySQL 写入失败（事务回滚），需**补偿删除已上传的 COS 对象**，避免产生孤儿文件。
- 补偿可同步执行（try-catch 中清理）或记录失败对象进「待清理队列」由定时任务清理。

### 2. 删除

- 顺序：**先删 MySQL（逻辑删除）→ 再从 CI 图库出库 → 再删 COS 对象**。
- COS 删除失败仅产生多余对象，不影响业务，可交由定时任务或后续清理；不建议删除失败回滚已提交的 MySQL 事务。

### 3. 批量抓取上传

- 批量上传中每张图片**独立事务**，单张失败不影响其他图片，也不回滚已成功的图片。

## 六、分库分表事务

### 1. 单库分表的本地事务

本项目当前为**单库分表**（一个 MySQL 实例，`picture` + `picture_{spaceId}` 多张物理表），ShardingSphere-JDBC 底层复用同一物理连接，因此：

- 跨分表的写入（如同一空间内的多张图片操作）**仍由本地事务保证原子性**，无需引入分布式事务。
- 只有当未来演变为**真正的多数据源分库**时，才需引入 XA 事务（Atomikos/Narayana）或 Seata 柔性事务。

### 2. 动态建表 + 刷分片规则的顺序与回滚

空间创建流程涉及「业务数据写入」与「分片基础设施变更」，二者性质不同，拆分处理：

1. **业务事务**（本地事务）：`insert space` + `insert space_user` 提交。
2. **基础设施变更**（事务外，顺序执行）：
   - 先 `CREATE TABLE picture_{spaceId} LIKE picture` 建表；
   - 再调用 `DynamicShardingManager` 刷新分片规则（`alterRuleConfiguration`）。
3. **异常处理**：
   - 建表失败 → 不刷新规则，回滚（或标记）该空间为「初始化失败」，业务侧禁止向该空间写图；
   - 刷规则失败 → 表已存在但规则未生效，需记录并重试刷新，避免「路由到不存在表」。
4. **顺序保证**：严格「先建表、后刷规则」，防止新空间写入时路由到尚不存在的物理表（对应《分库分表专项设计文档》注意事项第 4 条）。

## 七、工程使用规范

### 1. `@Transactional` 使用位置

- 标注在 `service` 实现类的 **public** 方法或类上，不在 controller、mapper 标注。
- 方法内避免耗时操作（如 COS 上传、远程调用、图片处理），减少事务与数据库锁的持有时间；此类操作放到事务提交之后。

### 2. 事务失效陷阱

以下写法会导致事务不生效或不符合预期，实现时需规避：

| 陷阱 | 说明 |
| --- | --- |
| 同类自调用 | 方法 A 调 `this.methodB()`，`methodB` 的 `@Transactional` 不经过 AOP 代理而失效 |
| 非 public 方法 | `@Transactional` 只对 public 方法生效 |
| checked 异常不回滚 | 默认仅 `RuntimeException` / `Error` 触发回滚；需回滚受检异常时用 `@Transactional(rollbackFor = Exception.class)` |
| 异常被吞掉 | catch 中未重新抛出，事务感知不到异常而不回滚 |
| 方法未被 Spring 管理 | 通过 `new` 创建的类，其事务注解无效 |

### 3. 只读事务

纯查询方法可标注 `@Transactional(readOnly = true)`，利用数据库优化并防止误写；非必要不强制。

### 4. 事务与缓存一致性

- 项目存在多级缓存（Caffeine + Redis）。**缓存更新/删除应放在事务提交之后**，避免事务回滚后缓存与数据库不一致。
- 优先采用「删除缓存」而非「更新缓存」，待下次读时重建，降低脏缓存概率。

## 八、各模块事务边界一览表

| 模块 | 事务类型 | 关键约束 |
| --- | --- | --- |
| 用户注册/登录 | 本地事务（注册）/ 无（登录查询 + Redis 会话） | 注册依赖唯一索引兜底 |
| 空间创建 | 本地事务（space + space_user）+ 事务外建表/刷规则 | 严格先建表后刷规则 |
| 空间删除 | 本地事务（space + space_user + picture 逻辑删除） | 级联删除原子 |
| 空间成员管理 | 本地事务 | 唯一索引兜底 |
| 图片上传 | 本地事务（MySQL）+ 最终一致（CI 图库/COS 补偿） | 先 COS 后 DB，失败补偿清 COS |
| 图片删除 | 本地事务（MySQL）+ 最终一致（CI 图库出库 + COS 清理） | 先 MySQL 后 CI 图库/COS |
| 图片编辑/查询 | 本地事务 / 只读事务 | — |
| 以图搜图 | 只读（CI 检索 + MySQL 回查） | 以 MySQL 为准过滤 |
| 空间分析 | 只读 | — |
