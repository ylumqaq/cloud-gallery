# 阶段 6：分库分表（已完成）

> 本阶段状态：已完成。以下为结合实际代码的落地内容，按「写代码时的实现步骤」组织。

## 一、阶段目标

实现按 `space_id` 分表（ShardingSphere 5.5.3 自定义分片 + 动态建表 + 运行时规则刷新），验收标准：

- `space_id` 为空落到 `picture`，非空落到 `picture_{space_id}`
- 团队空间创建时自动建表
- 查询 / 写入正确路由到对应分表

## 二、方案概述与关键决策

### 1. 分片方案

| 项 | 内容 |
| --- | --- |
| 分片键 | `space_id` |
| 逻辑表 | `picture` |
| 路由规则 | `space_id` 为空 → `picture`；非空 → `picture_{space_id}` |
| 分片方式 | 标准分片 `StandardShardingAlgorithm`（仅需 `space_id = ?` 等值精确路由） |
| 动态建表 | 空间创建时执行 `CREATE TABLE picture_{space_id} LIKE picture` |
| 规则刷新 | 扫描已存在的 `picture_*` 物理表重建 `actual-data-nodes`，运行时刷新分片规则 |

### 2. 集成方式选型（关键决策）

在 ShardingSphere 5.5.3 下有两种集成方式，本阶段选择**编程式 Java 配置**（`ShardingSphereDataSourceFactory.createDataSource`），而不是官方的 `ShardingSphereDriver + YAML` 方式，理由：

- 项目使用 MySQL 业务库，编程式方式与现有 `DataSourceConfig` 结构最兼容，可把 MySQL 物理数据源就地包装为 ShardingSphere 主数据源；
- 需要**运行时动态刷新规则**，编程式方式能直接持有 `ShardingSphereDataSource` 引用（再反射取出 `ContextManager`），便于 `DynamicShardingManager` 刷新规则。

### 3. ShardingSphere 5.5.3 的三个重要变化（踩坑背景）

1. **核心功能改为「可选插件」**：`shardingsphere-jdbc` 的 pom 中，`sharding-core`、MySQL SQL 解析、单机模式、数据源池、权限等模块均为 `test` scope，**不会随 `shardingsphere-jdbc` 传递**，必须显式引入；
2. **单表不再自动加载**：从 5.4.0 起，`user` / `space` 等未分片表必须显式配置 `SINGLE` 规则，否则报 `TableNotFoundException`；
3. **动态刷新 API 变更**：5.5.3 的 `ContextManager` 已没有 `alterRuleConfiguration` 方法，`ShardingSphereDataSource` 也不再公开 `getContextManager()`，需改用 `DatabaseRuleConfigurationManager.refresh(...)` + 反射获取 `ContextManager`。

### 步骤 2：实现 PictureShardingAlgorithm 自定义分片算法

新建 `manager/sharding/PictureShardingAlgorithm.java`，实现 `StandardShardingAlgorithm<Long>`：

```java
public class PictureShardingAlgorithm implements StandardShardingAlgorithm<Long> {

    /**
     * 精确分片：根据分片值（space_id）决定落到哪张物理表。
     */
    @Override
    public String doSharding(Collection<String> availableTargetNames,
                             PreciseShardingValue<Long> shardingValue) {
        Long spaceId = shardingValue.getValue();
        String logicTable = shardingValue.getLogicTableName();
        // 公共图库（space_id 为空）落到逻辑表 picture，否则落到 picture_{spaceId}
        return spaceId == null ? logicTable : logicTable + "_" + spaceId;
    }

    /**
     * 范围分片：业务当前不涉及按 space_id 范围查询，返回空集合即可。
     */
    @Override
    public Collection<String> doSharding(Collection<String> availableTargetNames,
                                         RangeShardingValue<Long> shardingValue) {
        return Collections.emptyList();
    }
}
```

设计要点：

- 分片键泛型为 `Long`，与实体 `Picture.spaceId` 类型一致；
- `doSharding` 只读取 `getValue()` 与 `getLogicTableName()`，返回不带数据源前缀的物理表名；
- 算法类通过 `CLASS_BASED` 算法配置中的 `algorithmClassName` 反射实例化，因此无需实现 `getType()` / `init()`（接口已有 default 空实现）。

            @Qualifier("mysqlDataSource") DataSource physicalDataSource) {
        this.shardingSphereDataSource = shardingSphereDataSource;
        this.physicalDataSource = physicalDataSource;
    }
    // ...
}

**3.1 建表 + 刷新的入口（供业务调用）**

```java
/**
 * 为指定空间创建图片分表并刷新分片规则。
 */
public void createTableForSpace(Long spaceId) {
    if (spaceId == null) {
        return;
    }
    // 先建表，保证结构一致（与 picture 表完全一致）
    createPictureTable(spaceId);
    // 再刷新规则，让新建的分表立即参与路由
    refreshShardingRule();
}
```

**3.2 建表（走底层物理数据源，绕过 ShardingSphere）**

```java
private void createPictureTable(Long spaceId) {
    String tableName = LOGIC_TABLE + "_" + spaceId;
    String sql = "CREATE TABLE IF NOT EXISTS `" + tableName + "` LIKE `" + LOGIC_TABLE + "`";
    try (Connection connection = physicalDataSource.getConnection();
         Statement statement = connection.createStatement()) {
        statement.executeUpdate(sql);
    } catch (SQLException e) {
        throw new BusinessException(ErrorCode.SYSTEM_ERROR, "创建图片分表失败：" + tableName);
    }
}
```

要点：`CREATE TABLE ... LIKE ...` 是 DDL，必须用底层物理数据源执行（ShardingSphere 无法路由 DDL）。

**3.3 运行时刷新规则（反射拿 ContextManager）**

```java
private void refreshShardingRule() {
    List<String> tables = scanPictureTables(physicalDataSource);
    String actualDataNodes = buildActualDataNodes(tables);
    ShardingRuleConfiguration ruleConfig = buildRuleConfig(actualDataNodes);

    ContextManager contextManager = getContextManager();
    try {
        contextManager.getMetaDataContextManager()
                .getDatabaseRuleConfigurationManager()
                .refresh(DATABASE_NAME, ruleConfig, true);
    } catch (SQLException e) {
        throw new BusinessException(ErrorCode.SYSTEM_ERROR, "刷新分片规则失败");
    }
}

private ContextManager getContextManager() {
    try {
        Field field = shardingSphereDataSource.getClass().getDeclaredField("contextManager");
        field.setAccessible(true);
        return (ContextManager) field.get(shardingSphereDataSource);
    } catch (NoSuchFieldException | IllegalAccessException e) {
        throw new BusinessException(ErrorCode.SYSTEM_ERROR, "获取 ShardingSphere ContextManager 失败");
    }
}
```

要点：

- 5.5.3 的 `ShardingSphereDataSource` 内部持有 `private final ContextManager contextManager` 字段但未公开 getter，通过反射读取；
- 刷新走 `MetaDataContextManager → DatabaseRuleConfigurationManager.refresh(databaseName, ruleConfig, true)`，是 5.5.3 中替代旧 `alterRuleConfiguration` 的官方 API。

**3.4 共享的静态规则构建工具（供配置类与刷新逻辑复用）**

```java
// 扫描 MySQL 业务库中已存在的图片物理表（含公共图库 picture）
public static List<String> scanPictureTables(DataSource physicalDataSource) {
    List<String> tables = new ArrayList<>();
    tables.add(LOGIC_TABLE); // 公共图库固定使用 picture 表
    String sql = "SELECT table_name FROM information_schema.tables "
            + "WHERE table_schema = DATABASE() AND table_name LIKE 'picture\\_%' ORDER BY table_name";
    try (Connection connection = physicalDataSource.getConnection();
         Statement statement = connection.createStatement();
         ResultSet resultSet = statement.executeQuery(sql)) {
        while (resultSet.next()) {
            tables.add(resultSet.getString("table_name"));
        }
        return tables;
    } catch (SQLException e) {
        throw new BusinessException(ErrorCode.SYSTEM_ERROR, "扫描图片分表失败");
    }
}

// 构建 actual-data-nodes，例如 cloud_gallery.picture, cloud_gallery.picture_1
public static String buildActualDataNodes(List<String> tables) {
    return tables.stream()
            .map(table -> DATABASE_NAME + "." + table)
            .collect(Collectors.joining(", "));
}

// 构建图片表分片规则（CLASS_BASED + STANDARD 策略指向 PictureShardingAlgorithm）
public static ShardingRuleConfiguration buildRuleConfig(String actualDataNodes) {
    ShardingTableRuleConfiguration tableRule =
            new ShardingTableRuleConfiguration(LOGIC_TABLE, actualDataNodes);
    tableRule.setTableShardingStrategy(
            new StandardShardingStrategyConfiguration(SHARDING_COLUMN, ALGORITHM_NAME));

    Properties algorithmProps = new Properties();
    algorithmProps.setProperty("strategy", "STANDARD");
    algorithmProps.setProperty("algorithmClassName", ALGORITHM_CLASS);
    AlgorithmConfiguration algorithmConfig = new AlgorithmConfiguration("CLASS_BASED", algorithmProps);

    ShardingRuleConfiguration ruleConfig = new ShardingRuleConfiguration();
    ruleConfig.setTables(Collections.singletonList(tableRule));
    ruleConfig.setShardingAlgorithms(Collections.singletonMap(ALGORITHM_NAME, algorithmConfig));
    return ruleConfig;
}
```

要点：

- 扫描用 `information_schema.tables` + `DATABASE()`，直接拿到真实物理分表，比查 `space` 表更贴近「分表即事实」；
- 扫描 / 构建规则做成 `static`，既供 `ShardingSphereConfig` 在启动时构建初始规则，又供 `refreshShardingRule` 动态刷新复用，避免循环依赖（配置类依赖静态方法，不会触发 `DynamicShardingManager` 实例化）。

### 步骤 5：新建 ShardingSphereConfig 创建主数据源

新建 `config/ShardingSphereConfig.java`，把 MySQL 物理数据源包装为 ShardingSphere 分片数据源并作为 `@Primary` 主数据源：

```java
@Configuration
public class ShardingSphereConfig {

    @Bean("shardingSphereDataSource")
    @Primary
    public DataSource shardingSphereDataSource(
            @Qualifier("mysqlDataSource") DataSource mysqlDataSource) throws SQLException {
        // 扫描已存在的物理分表，构建初始 actual-data-nodes 与分片规则
        List<String> tables = DynamicShardingManager.scanPictureTables(mysqlDataSource);
        String actualDataNodes = DynamicShardingManager.buildActualDataNodes(tables);
        ShardingRuleConfiguration ruleConfig = DynamicShardingManager.buildRuleConfig(actualDataNodes);

        // 单表规则：user / space / space_user 不分片，需显式声明（5.4+ 不再自动加载单表）
        SingleRuleConfiguration singleRuleConfig = new SingleRuleConfiguration();
        singleRuleConfig.setTables(Arrays.asList(
                DynamicShardingManager.DATABASE_NAME + ".user",
                DynamicShardingManager.DATABASE_NAME + ".space",
                DynamicShardingManager.DATABASE_NAME + ".space_user"));

        Collection<RuleConfiguration> rules = Arrays.asList(ruleConfig, singleRuleConfig);
        // mode 传 null 使用默认 Standalone（内存）模式
        return ShardingSphereDataSourceFactory.createDataSource(
                DynamicShardingManager.DATABASE_NAME, null, mysqlDataSource, rules, new Properties());
    }
}
```

设计要点：

- 用 `createDataSource(String databaseName, ModeConfiguration, DataSource, Collection<RuleConfiguration>, Properties)`，`databaseName` 同时作为数据源名（`cloud_gallery`），与 `actual-data-nodes` 前缀一致；
- `mode` 传 `null` 走默认 Standalone（内存）模式；
- 规则集合同时包含 **SHARDING**（picture 分片）和 **SINGLE**（user/space/space_user 单表），两者缺一不可。

### 步骤 6：SpaceServiceImpl 接入「空间创建即建表」

修改 `service/impl/SpaceServiceImpl.java`，注入 `DynamicShardingManager` 并在空间落库成功后触发建表：

```java
@Resource
private DynamicShardingManager dynamicShardingManager;

@Override
public long addSpace(SpaceAddRequest request) {
    // ...校验空间类型，组装 Space 并 save...

    boolean saved = this.save(space);
    if (!saved) {
        throw new BusinessException(ErrorCode.SYSTEM_ERROR, "创建空间失败");
    }
    // 空间落库成功后，动态建图片分表并刷新分片规则（业务事务外顺序执行）
    dynamicShardingManager.createTableForSpace(space.getId());
    return space.getId();
}
```

要点：

- 私有 / 团队空间均按 `space_id` 分表，因此两种类型都建表（分片算法对非空 `space_id` 一视同仁）；
- 建表在 `save(space)` 成功后执行，且 DDL 隐式提交、不在业务事务内回滚，符合《事务设计文档》「建表与刷规则在业务事务外顺序执行」。

@AutoConfigureMockMvc
class PictureShardingEndToEndTest {

    private MockMvc mockMvc;

## 四、问题修复记录

| 问题 | 现象 | 根因 | 修复 |
| --- | --- | --- | --- |
| 分片 / 解析 / 模式模块缺失 | 引入 `shardingsphere-jdbc` 后仍报找不到分片规则相关类 | `shardingsphere-jdbc` 的 pom 将 `sharding-core`、MySQL 解析、单机模式等标为 `test` scope，不传递 | 显式引入 `sharding-core` / `parser-sql-engine-mysql` / `standalone-mode-core` / `standalone-mode-repository-memory` |
| Hikari 连接属性提取失败 | 启动报 `Cannot invoke "Object.toString()" because "Map.get(Object)" is null`（`StorageUnit` 取不到 `url`） | ShardingSphere 缺少 Hikari 数据源识别 SPI，无法从 `HikariDataSource` 提取 `url` / `username` | 引入 `shardingsphere-infra-data-source-pool-hikari` |
| `Strings` 类缺失 | 启动报 `ClassNotFoundException: org.apache.commons.lang3.Strings` | ShardingSphere 5.5.3 依赖 commons-lang3 3.20.0（含 `Strings`），项目传递依赖被降到旧版本 | 显式声明 `commons-lang3:3.20.0` 覆盖 |
| 权限提供器缺失 | 启动报 `No implementation class load from SPI 'PrivilegeProvider' with type 'ALL_PERMITTED'` | 默认 `ALL_PERMITTED` 权限实现位于 `authority-simple`，未引入 | 引入 `shardingsphere-authority-simple` |
| 单表路由失败 | 注册接口报 `Table or view 'user' does not exist` | ShardingSphere 5.4.0 起不再自动加载单表 | 显式配置 `SingleRuleConfiguration`（user / space / space_user） |
| 动态刷新 API 变化 | 原设计文档的 `contextManager.alterRuleConfiguration` 不存在 | 5.5.3 已移除该方法 | 改用 `DatabaseRuleConfigurationManager.refresh(...)`，并通过反射获取 `ContextManager` |

> 附带说明（非 bug，但需知悉）：集成测试（`@Transactional`）中创建空间会触发 `CREATE TABLE`，而 MySQL 的 DDL 隐式提交、无法回滚，因此跑完测试会在数据库残留空的 `picture_*` 分表。这是「空间创建自动建表」的固有特性，不影响功能；如需保持测试库干净，可在测试后清理 `picture_%` 表。
